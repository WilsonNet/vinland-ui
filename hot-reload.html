Hot reload

Optional: edit, save, and the running window picks up the new code in about a second, keeping its state. A plain odin build stays the default.

Odin compiles a whole app in about a second, so rebuilding by hand is already fast. What a rebuild loses is the running state: the page you navigated to, a half-filled form, the scroll position, dark mode. vui-hot keeps the process and the window alive and swaps only the code, so a save shows its effect in place. It is a development tool and entirely optional: the same package still builds with odin build into a normal executable that contains no reload code.

What survives a reload

ClassEffect
window, GPU device, GL contextnever recreated; the swap itself takes about 2 ms
ui.Contextwidget state (scroll offsets, focus, hover, text edits, animations), caches, fonts, icons, images
app.keep(&global)your state, carried over and migrated when its type changes
other package globalsstart from their initial values in the new build (setup fills them again)

An app written as an app.Program gets all of the above. setup runs on every load (the first start and after each reload): register fonts, icons and lookup tables there (vui's register procs are idempotent by name), call app.keep on the globals that hold state, and set a.on_command. init runs once per window, so initial values are not reapplied after a reload. A classic for app.next_frame loop also reloads, but its own defers close the window, so it reopens on every reload (kept globals still carry over).

Changing types while it runs

A kept value is copied as-is when its type is unchanged. When the type changed it is migrated instead of thrown away: struct fields are matched by name (recursively), fixed arrays element by element, and integers and floats are converted when only their size changed. New fields keep their default, removed fields are dropped, and a field whose type changed in an incompatible way is reset. A value is never reinterpreted and an integer that does not fit its new type is not wrapped. vui-hot prints what happened, and vui-ctl info lists it under hot.notes.

An edit to vui itself that changes the layout of App or ui.Context cannot be swapped under a live window: the old build closes it, the new build opens a new one in the same process, and kept globals are still restored.

When something goes wrong

ClassEffect
compile errorthe previous build keeps running; the compiler output is drawn over the app and printed in the terminal
crash right after a reloadthe app restarts on the previous good build and shows which build crashed
crash laterthe app restarts on the current build; after 3 crashes in 10 s vui-hot waits for the next change
edit during a buildthe stale compile is cancelled and the newest code is built
vui-hot stops (Ctrl+C, killed)the app exits with it; old builds are deleted

A restart after a crash starts the app fresh: kept state lives in the crashed process. Element ids come from source locations, so an edit that moves lines above a stateful element (a scroll container, a focused input) can reset that element; give it a ui.key to pin it.

Options

ClassEffect
-collection:name=dirpassed to odin and used to follow imports (vinland is found automatically)
-<odin flag>any other odin flag, e.g. -o:none or -define:X=1 (default -debug)
--watch <path>also watch a file or directory
--out <dir>build directory (default build/hot/<package>)
--poll <ms> / --debounce <ms>scan interval (100) and quiet period after a change (30)
--no-restart / --quietexit when the app crashes / print only errors
-- <args>arguments for the app
VUI_HOT_OVERLAY=0hide the in-window build status

vui-hot watches the package directory, every local package it imports and every file it pulls in with #load; it re-reads imports after each edit, so a newly imported package is watched at once. A save that leaves the bytes unchanged never rebuilds. Polling costs well under 1% of one core.

Cost and limits

A reload costs the compile (about 1.1 s for the showroom, the same as a normal build) plus about 2 ms to swap the library in. Every previous build stays mapped until the app exits, because live state can still point at its string literals and code; the kernel can drop those pages, and each build releases its scratch arenas when it hands over. For the showroom, private memory grows by a few MB per reload at first and levels off (32 MB at start, 76 MB after 12 reloads, 80 MB after 24). Keep the build directory on disk rather than tmpfs (vui-hot warns), where mapped old builds could never be dropped.

Procedure values stored in kept state keep calling the build that created them until they are assigned again, which setup usually does. State shared with another thread should be kept through a pointer so both sides see the same object. Hot reload is tested on Linux and macOS (the end-to-end suite runs on both in CI); Windows is untested (see PLATFORMS.md).

Driving it from tests and agents

Under vui-hot, vui-ctl info adds a hot object: generation, reloads, status (Idle, Building, Error), error, build_ms, swap_ms, pid and notes. A script can save a file and poll until generation increases. tests/hot/test_hot.py runs the whole matrix sandboxed (VUI_HIDDEN=1).
